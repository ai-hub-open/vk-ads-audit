## 1. Формат отчёта

Порядок разделов HTML:

1. **Шапка** — период, путь (A/B), опорный CPA и источник (как сейчас).
2. **Плитки KPI** + блок Метрики (как сейчас).
3. **Чек-листы по блокам A–G** — таблица «проверка · ✅/❌/— · коротко почему», под ней **балл блока «n / m»**.
   - ✅ — проверка пройдена, ❌ — не пройдена, **— — «не проверено»**: данных нет (поле не пришло из API, путь A,
     нет Метрики) или проверка неприменима (нет групп с этой целью). «—» не входит в знаменатель.
   - Общий балл аудита — сумма по блокам «Σn / Σm».
4. **Находки** — как сейчас: 🔴 → 🟠 → 🟢 → ⚪, внутри по ₽-эффекту; карточка с доказательством, надёжностью,
   действием, «Объяснено клиентом». Каждая находка ссылается на проверку чек-листа (`check`).
5. **Вопросы к клиенту** — то, что эксперты считают важным, а API не показывает (раздел 3). Вопрос, к которому данные
   дают повод, помечается «важно для вашего кабинета» с причиной.
6. **Ограничения** — как сейчас + строка на каждую проверку «— не проверено» с причиной.

Чек-лист и находки — разные вещи: чек-лист отвечает «настроено ли», находки — «сколько это стоит и что делать».
Не каждая ❌ даёт находку (например, «не тестировались форматы» при выполненном KPI — только ❌ в чек-листе).

## 2. Проверки

Контракт проверки (новый, в `scripts/checks.py`): `id · блок · статус (pass/fail/na) · причина · связанные находки`.
Находки — прежний контракт `diagnose.finding` + поле `check`.
«Как»: **API** — поле подтверждено живым ответом; **API?** — поле по документации, имя подтверждается живым прогоном;
пока поля нет в данных — статус «—» с причиной «поле не получено из API»; **Метрика**; **Клиент** — только вопрос.

## 3. Вопросы к клиенту (`references/client-questions.md`)

Постоянный список; вопрос получает пометку «важно для вашего кабинета», если данные дают повод:
события пикселя (есть цель «конверсии»); CRM и офлайн-конверсии; лид-форма — сколько полей и есть ли уточняющий вопрос
(есть цель «лид-формы»); сообщество — мобильная версия, меню, активность (есть цель «подписка»/«сообщения»);
уведомления менеджерам и ответ ≤ 15 минут, автоответ/квиз; классы лидов A/B/C/D и стоимость A+B; следующий шаг сделки;
лендинг — скорость, мобильная версия (Метрика показывает долю мобильных); соответствие аудиторий и креативов ЦА;
не слишком ли узкие интересы.

## 4. Решения по расхождениям экспертов (Лиза, 2026-10-15)

1. Свежесть креативов: ⚪ после 14 дней, 🟠 после 28.
2. Частота: 🟠 от 3 при падении CTR, 🔴 больше 5.
3. Креативов в группе: норма 2–5.
4. Дневной бюджет: 🟠 ниже 300 ₽ (порог платформы), ⚪ 300–500 ₽.
5. Окно решения: выводы по объявлениям — не раньше 7 дней работы.
6. Обучение автостратегии: меньше 15 конверсий за 7 дней работы.

## 5. Данные

- Глубокий аудит по умолчанию — 30 дней: окна 7 / 14 / 30 считаются из дневной статистики, новых вызовов не нужно.
  Период < 30 дней — F4 по доступным окнам, недоступные — «—».
- `collect.py`: в `BANNER_FIELDS` добавить `call_to_action`; поля для API?-проверок (erid/маркировка, авто-UTM,
  исключения, минус-фразы, период и расширение ключевых фраз, корректировки, тип и размер сегмента, дата обновления
  списка, CBO) — запрашивать по документированным именам; неизвестные имена сервер игнорирует, пустое → «—».
- `normalize.py`: слой группы (тёплый / LAL / холодный) по таргетингу; формат и соотношения объявления по `content`;
  дни работы группы и объявления; окна 7/14/30.
- Пороги — `references/thresholds.json` (новые ключи с источником); словарь `cta_words` и шаблоны имён по умолчанию — там же.

## 6. Тесты и релиз

- На каждую проверку — случаи pass / fail / «—» (поле отсутствует); на каждую новую находку — срабатывает / нет.
- Эталонные кабинеты: обновить 5 существующих (ожидаемые наборы находок и баллы блоков) + кабинет `expert_full`,
  где каждая проверка чек-листа даёт ❌.
- Живой прогон (гейт 0.1.0) дополнительно закрывает имена полей всех API?-проверок.
