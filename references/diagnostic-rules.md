# Правила диагностики — методика v1

Источники методики — экспертный слепок, утверждённый Лизой 2026-10-15: [01] VC.ru «аудит 2026»,
[02] VC.ru «Запуск VK Ads в 2026», [03] bizon.ru «гайд 2026», [04] слайды агентского аудита, [D] дайджест
VK Рекламы (август 2026). «Решение Лизы» — выбор там, где эксперты расходились (раздел «Решения по расхождениям»).
«Платформа» — требование самой VK Рекламы; «черновик 0.1» — правило версии до методики, оставлено без изменений.

Аудит состоит из двух слоёв. **Чек-лист** (блоки A–G, `scripts/checks.py`) отвечает «настроено ли».
**Находки** (правила в `scripts/diagnose.py`, функция `(ds, th, ctx)`, зарегистрирована `@rule`) отвечают
«сколько это стоит и что делать». У каждой находки есть поле `check` — id проверки чек-листа, к которой она относится
(`CHECK_OF` в `diagnose.py`). Не каждая ❌ даёт находку: «не тестировались форматы» (`E5`) и блоки C1–C6, C16 —
только строка чек-листа. Числа берутся из `references/thresholds.json`, уровни: 🔴 срезать слив → 🟠 починить →
🟢 масштабировать → ⚪ гигиена.

«Группа» здесь — `campaign` VK (в интерфейсе «Группа»); «живая» — не `deleted` и не в архиве (`issues` с кодом `ARCHIVED`), «активная» — статус из
`active_statuses` (`active`) **и кампания не остановлена**: группа со статусом `active`, у которой кампания (`ad_plan`)
в статусе `blocked` или `deleted` или есть issue `AD_PLAN_STOPPED`, — «на паузе (кампания остановлена)», а не активная
(единый помощник `features.is_active_group`: гейты чек-листа, лидеры, дубли таргетингов C12, D4, быстрый анализ). Удалённые и архивные группы правила игнорируют вместе с их объявлениями (расход архивных остаётся в итогах кабинета).

Опорный CPA: целевой клиента → иначе медиана CPA живых групп с ≥ `min_conversions_for_cpa` конверсиями → иначе нет
(`ref_source`: `target` / `median` / `none`; попадает в находки и шапку отчёта).
Надёжность находки по кликам: ≥ `confidence_high_clicks` — надёжно, ≥ `confidence_medium_clicks` — средне,
меньше — мало данных. Автостратегия определяется по `autobidding_mode` из списка `auto_bidding_modes`
(сейчас `max_goals`), а не по «непустому значению». `second_price_mean` — **ручная ставка** (ставка в `price`,
фактический CPM; подтверждено 16.10.2026), список `manual_bidding_modes`: это не автостратегия — правила автостратегии
(`low_budget` для обучения, `learning_starved`) её не судят, а `cap_too_early` не считает ручную ставку «предельной ценой»;
ручная ставка в первые 7 дней — не «ограничение ставки на старте» (решение Лизы: только классификация, без новой находки).
В отчёте режим называется по словарю `bidding_mode_labels` («автостратегия», «ручная ставка»); неизвестный режим — «—».

Покрытие данных. Правила по объявлениям (`no_active_banners`, `banners_per_group`, уровень объявлений в `low_ctr`,
правила блока E) смотрят только группы из `coverage.banner_groups` — те, для которых был вызов
`vk_ads_banners_list`; на пути A объявления есть лишь у части групп, у остальных вывод «нет объявлений» был бы
выдумкой. Правила по статистике работают с `_measured` — живые группы без пометки `stats_missing` (статистика по
группе не получена ни по дням, ни старой сводкой); такие группы отчёт перечисляет в «Ограничениях».
Итоги периода — сумма `statistics_day` (сводка всё время подставляется только в старом `raw/` без единого дневного вызова; группа без дневных данных при наличии таких вызовов — `stats_missing`); частота и охват известны только группам, созданным внутри периода (иначе `None`:
`burnout` молчит, `F3` — «unknown»).

**Признак, поле которого не получено из API, — `None`; правило по `None` молчит, а проверка получает статус
«unknown», не «fail».** Это главное правило методики: «не получено» ≠ «плохо».

## Статусы чек-листа

Каждая проверка получает один из шести статусов (`scripts/checks.py`).

| Статус | В отчёте | Смысл | В балле |
|---|---|---|---|
| `pass` | ✅ | проверка пройдена | в числителе и знаменателе |
| `fail` | ❌ | не пройдена: сработала хотя бы одна находка её правил либо признак не используется | в знаменателе |
| `unknown` | — | **данных нет**: поле не пришло из API, путь A, нет Метрики, объявления собраны не по всем группам | не входит; уходит в «Ограничения» строкой «Не проверено «<проверка>»: <причина>» |
| `na` | — | **нечего проверять**: проверка неприменима (нет групп с этой целью, нет ключевых фраз, нет LAL-сегментов) либо её правила не сравнили ни одной сущности с порогом; для воронок B1 — клиент ответил «не применимо». Нет активных групп — «нечего проверять: нет активных групп» у всех пунктов по группам и объявлениям (а не «поле не получено» или «статистика не собрана»: в кабинете, где все группы удалены, собирать было нечего); группы есть, а активных объявлений нет — «нечего проверять: нет активных объявлений» у пунктов о свойствах объявлений (A2, A3, E1, E2, E4–E7; E3 при этом ❌ — находка `no_active_banners`). Гейт `na` никогда не прячет сработавшую находку | не входит; в «Ограничения» не попадает |
| `ask` | ❓ | **уточнить у клиента**: воронка подписки, лид-формы или Senler не используется — это не ошибка, пока клиент не ответил. Причина «воронка не используется — уточнить у клиента»; вопрос `funnel_*` в «Вопросах к клиенту» | не входит; в «Ограничения» не попадает |
| `potential` | 🟢 | клиент подтвердил, что воронка подходит, но не используется: «потенциал роста: <ответ>» | не входит; даёт 🟢-находку `funnel_potential` |

Статусы `ask` и `potential` — только для воронок `B1.subscription`, `B1.leadform`, `B1.senler`. Ответы клиента лежат в
`client_answers.json` (формат — `references/client-questions.md`) и ставят только `na` / `potential`: ✅ и ❌ они не
меняют. Нет ответа — `ask`.

`diagnose()` возвращает `evaluated` — для каждого правила число сущностей, реально сравнённых с порогом
(`_seen`); молчаливые пропуски не считаются. `run_checks` ставит `na`, если сумма `evaluated` по правилам проверки
равна нулю и находок нет: чек-лист не рисует ✅ за молчание правила, которому было нечего проверять.

**Балл блока — «n / m»**: n — число `pass`, m — число `pass` + `fail`. Блок без проверяемых строк показывает «—».
**Общий балл** — «Σn / Σm» по блокам A–G. Нет ни одной живой группы — общий балл не считается (`total` — `null`,
`idle` — «кабинет не откручивает: нет живых групп», а если расход был у архивных групп — «нет живых групп — общий балл не считается»), отчёт пишет это вместо балла. `F5` («Решения не раньше 7 дней
работы») — в балл не входит: обычно `na` с причиной, сколько групп и объявлений моложе 7 дней (нет активных групп —
«нечего проверять: нет активных групп»); статистика не собрана или получена не по всем активным группам — `unknown`.

## Блок B. Структура аккаунта

Слой группы определяется по таргетингу: нет пользовательских сегментов — холодный (`cold`); есть сегмент LAL
(имя или описание содержит lookalike / LAL / «похож») — `lal`. Остальное — по связям сегмента (`relations[].object_type`,
MCP 0.12.0, подтверждено третьим живым прогоном): `remarketing_counter` (пиксель) или тип с `users_list` / `user_list`
(база) — тёплый (`warm`, ретаргетинг); `remarketing_search_phrases` — холодный, подтип «ключевые фразы» (`layer_subtype:
keywords`). У сегмента несколько связей разных типов — тёплый, если есть хоть один тёплый тип. Связей нет (старые `raw/`,
поле не пришло) или тип незнакомый — прежняя логика «не LAL — тёплый», но слой помечен `layer_guessed` (низкая
надёжность, как `stale_list` без связей): `B1.retargeting` не ✅ только потому, что сегмент не LAL, — «unknown»
(«ретаргетинг не подтверждён…»); `layer_share`, `mixed_plan` и `layer_missing` (когда не хватает холодного слоя) по
таким группам — карточки низкой надёжности с пометкой «(слои части групп определены по догадке)» и `tentative`: они не
ставят ❌, а `B2`, `B3`, `B4` получают «unknown». Таргетинги не получены — слой не определён, проверки слоёв — `unknown`.

## Решения по расхождениям экспертов

Решения Лизы, 2026-10-15; пороги вынесены в `thresholds.json`.

1. **Свежесть креативов:** ⚪ после 14 дней, 🟠 после 28 (`creative_stale_days`, `creative_stale_red_days`).
2. **Частота:** 🟠 от 3 при падении CTR, 🔴 больше 5 (`burnout_min_frequency`, `burnout_red_frequency`).
3. **Креативов в группе:** норма 2–5 (`min_active_banners_per_group`, `max_active_banners_per_group`).
4. **Дневной бюджет:** 🟠 ниже 300 ₽ (порог платформы), ⚪ 300–500 ₽ (`min_daily_budget_rub`,
   `recommended_daily_budget_rub`).
5. **Окно решения:** выводы по объявлениям и группам — не раньше 7 дней работы (`min_run_days`).
6. **Обучение автостратегии:** меньше 15 конверсий за 7 дней работы (`learning_min_conversions_per_week`).
